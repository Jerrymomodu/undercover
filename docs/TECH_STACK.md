# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, so each query is written once for both databases. With `DATABASE_URL` in its environment it uses the Supabase Postgres database through the session pooler, with every table in the `undercover` schema and at most 4 connections, which a request waits for rather than fails; otherwise SQLite, as in the tests. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. The payout rules are in `backend/payout.py`. `backend/scoring.py` scores evaluations, and is the only module that reads the answer key; seeding in `backend/database.py` is the only code that reads `data/evals/`. The backend reaches the agent's service, at `UNDERCOVER_AGENT` in the environment or `http://127.0.0.1:8002`, only through `backend/agent_service.py`: to start a dispatch or an evaluation, and after a handler's sign-off.
- `agent/`: five parts. `api.py` is the only way the agent reaches the backend: claims, runs, its instructions, the documents and the payout rules. `tools.py` holds every tool, the context they read and the claim graph's state, and each tool reads what it needs, such as the claim a claim agent is working on, from the agent's context through `ToolRuntime`. `harness.py` builds and runs the claim agent. `dispatcher.py` works a dispatch's or an evaluation's claims. `service.py` is the agent's service, a FastAPI app that the backend calls to start a dispatch or an evaluation and after a sign-off; in the cloud the agent runs as a service like this. `console.py` only sets up the report lines for the two ways the agent is started, `service.py` and `uv run -m agent CLM-1001`.
  - The claim agent is a hand-written LangGraph `StateGraph`, built by `claim_graph(llm, saver, instructions)`: a node that calls the model, a `ToolNode`, a pause for a sign-off with `interrupt()`, and a node that pays. Its nodes record each reply, tool call, tool result and section read on the claim, record each model reply's tokens and cost (OpenRouter's `usage.cost`) through the backend, return refusals to the model and limit the model calls. It saves its state after every step with LangGraph's `PostgresSaver` in the same Supabase database, with `durability="sync"`, so the agent always needs `DATABASE_URL`, even when the backend runs on SQLite. `connections()` opens the process's pool of at most 4 connections, and `ClaimAgent.graph()` builds each claim run's graph on a saver of its own on that pool, since a saver holds a lock around every read and write. The agent is synchronous throughout, because async Postgres connections don't work with Windows' default event loop.
  - The dispatcher is a LangGraph `StateGraph` with no model and no checkpointer: a node that lists the claims to work and fans out with one `Send` per claim, a worker node with `max_concurrency` set to N, and a node that finishes the run once every worker has finished. The worker's `RetryPolicy` retries `ModelRateLimitError` and `ModelTimeoutError`, carrying the claim on as the same attempt, and its `error_handler` leaves a claim whose waits ran out in progress, so no error stops the dispatch. LangGraph is at 1.2.22 or later, whose error handlers work with concurrent `Send` tasks.
  - The entry points are `work_on(claim_id, run, agent)`, the one function the dispatcher calls, which carries on a claim in progress or starts a waiting one; `work_claim(claim_id, graph, run_id)`, which works one claim as a new attempt; and `carry_on(claim_id, graph, run_id)`, which carries a claim on from its saved progress. Each run of the claim graph records how long it took, with its run.
  - Every claim graph run is traced in Langfuse, in a session named after the claim and its thread, and tagged with its dispatch's or evaluation's id.
  - It uses `openai/gpt-6-luna` with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort set. The backend's address is `UNDERCOVER_API` or `http://127.0.0.1:8000`. Like the dashboard, `uv run -m agent` reads it from the shell's environment, never `.env`; the agent's service gets `.env` from `npm run dev`.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests, with a stand-in for the agent's service.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key and the held-out claims.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `.env` holds the OpenRouter key (`OPENROUTER_API_KEY`), the Supabase session pooler connection string (`DATABASE_URL`) and the Langfuse keys (`LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_BASE_URL`).
